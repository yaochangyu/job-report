# v1-2 Report Shell Sync Plan

目標：讓 `https://yaochangyu.github.io/job-report/v1-2/traffic-overview/index.html` 這類報表網址，也能呈現和 `v1-1` 一樣的導覽頁殼、查詢條件與對應視角，而不是現在的獨立靜態頁。

原則：只共用外殼能力（導覽、查詢條件、網址參數、基礎樣式），**不共用各 dashboard 的內容欄位、KPI 結構、圖表配置與資料轉換邏輯**。每一個 dashboard 仍維持自己的 render 與資料契約，避免因欄位差異過大而互相牽連。

- [x] 盤點並接回 `v1-1` 的共用前端資產來源（例如 `app.js`、`app.css`、`dashboard-renderers.js`、`query-definitions.js`、`site-manifest.json`），確認要從哪個來源納入目前分支管理。這一步是必要的，因為現在 `v1-2` 線上有這些檔案，但目前工作分支沒有對應來源；若不先補齊來源，後續無法穩定修改與重新產出。
- [x] 調整 `v1-2` 的產出策略，讓各報表子路徑（例如 `traffic-overview/index.html`）不再輸出獨立報表頁，而是導向或載入同一套 SPA 殼，並自動切到對應視角。這一步是必要的，因為使用者目前是從子路徑直接進入報表；若只改根目錄首頁，深連結仍然不會有導覽頁與查詢條件；同時這一步只處理入口殼層，不改各 dashboard 自己的內容結構。
- [x] 保留並串接查詢條件行為，讓日期區間、頁面路徑與 view mode 能從子路徑初始化，且切換視角後仍沿用同一組查詢條件。這一步是必要的，因為你的需求不只要有外觀上的導覽頁，還要真正有 `v1-1` 那套共用查詢操作體驗；但查詢結果的欄位與呈現仍由各 dashboard 自己處理，不抽成共用欄位模型。
- [x] 調整 `run_all.py`、相關 render 流程與部署輸出內容，確保 build 後的 `output/` 與 GitHub Pages `v1-2/` 會一起帶出共用殼資產與子路徑入口檔。這一步是必要的，因為問題的根源在「產出結果」；若只改單一 HTML 範本，下一次重跑管線仍會被覆蓋回現在的樣子。
- [x] build 驗證 `v1-2/` 根目錄與各報表子路徑的實際輸出，確認都能進入同一套導覽殼，並在你確認需要時再執行測試。這一步是必要的，因為這次需求同時牽涉根入口、深連結與部署產物，必須確認不是只有其中一個網址正常。
